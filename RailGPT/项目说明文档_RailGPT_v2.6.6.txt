一、作品简介

1. 作品名称
RailGPT：面向铁路场景的多轮分析型智能体系统

2. 一句话概述
RailGPT 是一个聚焦铁路出行与铁路信息分析场景的智能体系统。它不是传统的一问一答聊天机器人，而是能够围绕“车次、车组、径路、经停、余票、中转、站点、线路关系”等铁路问题开展多轮分析、自动补充查询、整合多源信息并给出结构化回答的领域智能体。

3. 作品定位
本作品定位于“面向真实铁路信息场景的垂直智能体应用”。系统将大语言模型、铁路公开数据接口、领域知识库、对话记忆、任务规划和多轮推理机制结合起来，解决通用大模型在专业铁路问题中常见的以下不足：
（1）只会泛泛而谈，无法查询真实世界中的动态铁路信息；
（2）面对“今天有没有开”“是否停靠某站”“两地之间哪趟车最快”“某列车最近由哪组动车组担当”等问题时，容易出现幻觉或事实错误；
（3）缺乏上下文保持能力，无法围绕连续对话逐步完成复杂任务；
（4）缺乏可观测性，用户不知道系统当前在做什么、卡在哪里、是否真的调用了外部数据。

4. 目标用户
（1）普通铁路出行用户：关注余票、中转、到发站、乘车效率等问题；
（2）铁路爱好者与信息研究者：关注车组担当、运行径路、停站规律、图定开行等问题；
（3）需要进行铁路知识检索与场景问答的学生、研究者与演示观众；
（4）关注智能体在垂直行业真实落地的竞赛评委与技术观察者。

5. 作品核心价值
（1）把“会聊天”的模型升级为“会分析、会调用工具、会记忆上下文、会追问缺失信息”的领域智能体；
（2）把动态铁路数据、静态铁路知识和多轮对话记忆融合起来，提高回答的真实性与连续性；
（3）通过可观测状态机和思考面板，把智能体内部工作过程展示给用户，增强交互透明度；
（4）在工程上兼顾实时性、稳定性、缓存、限流、可扩展性和 UI 交互体验，为进一步比赛晋级与作品迭代打下基础。

6. 典型使用场景
（1）用户询问“G1234 最近由哪组车担当”，系统自动查询近 30 天担当记录并总结规律；
（2）用户询问“明天南京南到上海虹桥还有什么票”，系统通过 12306 余票接口返回车次、席别与余票情况；
（3）用户询问“G7511 明天停不停昆山南”，系统自动识别车次、日期和停靠站，调用经停查询工具核验后给出答案；
（4）用户先问“北京南到南京南明天有什么高铁”，再问“最早一班呢”“那它停不停徐州东”，系统能够继承上下文继续完成任务；
（5）用户希望了解某站、某线路、某区间的列车结构和运行特点，系统可结合本地知识库给出更完整的解释。


二、背景与需求

1. 问题背景
随着大语言模型的发展，用户越来越习惯于用自然语言提出问题，希望系统像“懂业务的助手”一样给出答案。然而在铁路场景中，问题通常兼具以下特点：
（1）强专业性：铁路场景存在大量专业实体，如车次、车组编号、站名、电报码、径路、经停、图定开行、正晚点、席别、中转方案等；
（2）强时效性：余票、运行图、开行日期、经停方案、担当关系等都可能随日期变化；
（3）强上下文性：用户往往不会一次把问题说完整，而是分多轮补充，例如先问区间，再追问最快车，再追问是否停靠；
（4）高真实性要求：一旦回答错误，用户很容易察觉，且会直接影响出行决策或造成信息误导。

通用聊天模型虽然语言表达能力强，但在铁路场景中存在明显短板：缺乏结构化查询能力、不了解真实接口、无法稳定处理专业实体、容易在缺失数据时“编答案”、难以继承连续上下文完成复杂任务。

2. 现有方案的不足
（1）纯搜索式系统虽然可以返回部分结果，但通常无法与自然语言分析结合；
（2）普通问答机器人可以聊天，却无法连接 12306、铁路数据接口或本地知识缓存；
（3）传统 FAQ 系统覆盖固定问题较好，但不具备复杂推理、跨工具协调和多轮补问能力；
（4）许多展示型 AI 项目强调界面，却没有真实的工具调用与数据闭环，难以支撑专业答辩中的技术追问。

3. 本项目的目标
RailGPT 试图构建一个“面向铁路专业场景的分析型智能体系统”，实现以下目标：
（1）支持自然语言输入，无需用户记住复杂命令；
（2）自动识别用户意图，并将问题拆解为合适的查询、分析、比较和总结任务；
（3）可连接多种真实铁路数据源，完成车次、车组、路径、余票、中转、站点等信息检索；
（4）在信息不足时主动补问，在信息足够时自动完成分析并生成自然语言答案；
（5）通过短期记忆、中期对话存档、长期记忆和知识检索增强连续对话能力；
（6）通过可视化状态与思考面板提高系统透明度；
（7）形成一个具备工程完整性、产品可用性与算法亮点的竞赛级作品。


三、功能介绍

1. 多轮自然语言铁路问答
系统支持用户直接用自然语言提问，例如“G218 最近谁担当”“明天苏州到上海最早的高铁是哪趟”“北京南到南京南有哪些车”“G7001 停不停常州北”等。系统会自动识别问题中的车次、区间、日期、站点、对象类型与任务目标，并进入相应的推理与查询流程。

2. 车次与动车组担当查询
系统支持以车次为入口查询近期动车组担当记录，也支持以动车组编号为入口回溯其近期服务历史。这类功能面向铁路爱好者和专业用户，能够回答“某车最近由哪组车担当”“某组车最近跑了哪些车次”等问题。

3. 列车径路与经停分析
系统支持查询某列车在指定日期的运行径路、站序与经停信息，并可进一步判断“是否停靠某站”。对于用户高频提问的“某趟车走哪条线”“是否经由某站”“停不停某站”等问题，系统能给出基于实时或近实时数据的分析结果。

4. 两站间列车目录与区间分析
系统提供区间车次目录查询能力，支持普通目录、快速摘要、基准对比、按出发时段筛选、按到达时段筛选、图定车与临客区分、担当局目录等不同形式。也就是说，系统不仅能回答“这两站之间有哪些车”，还可以从时段、效率、规则性和组织结构等角度做进一步分析。

5. 官方 12306 余票查询
系统对接 12306 相关查询链路，支持两站间余票查询。用户可以直接提问“明天南京南到上海虹桥还有票吗”“二等座多不多”等，系统能够给出结构化余票信息，并以更友好的文本形式反馈。

6. 官方 12306 中转查询
系统支持中转查询，可为用户寻找两站间的中转方案，必要时还可带入中转站信息。这使得系统从“信息检索型”智能体进一步扩展为“出行辅助型”智能体。

7. 站点信息与站名处理
系统内置站名与电报码能力，可进行站点信息查询、站名标准化、电报码转换等工作。由于铁路场景中站名表述多样、简称与正式名混用较多，这一能力对提升系统鲁棒性十分重要。

8. 上下文记忆与连续追问
系统支持连续对话中的上下文继承。例如用户先问“北京南到南京南明天有哪些高铁”，下一轮再问“最早一班是谁担当”“那它停不停济南西”，系统可以在前文基础上继续解析，而不是要求用户每轮都重新描述完整上下文。

9. 智能补问机制
当用户问题信息不足时，系统不会盲目回答，而会根据当前缺失槽位主动追问。例如用户只说“查一下明天余票”，系统会提示继续补充出发站和到达站；用户问“这趟车停不停”，系统会要求补充具体车次或站点。该机制显著降低了误答率。

10. 会话管理与历史归档
系统前端支持新建会话、切换会话、删除会话、重命名会话、搜索历史会话以及导出会话。后端通过本地会话存储将对话内容、记忆状态与上下文一并保存，方便用户后续回看或继续讨论。

11. 思考/状态可视化
系统前端提供观察面板，可显示系统思考流与程序状态词（PSW）。用户能够看到系统当前处于路由、规划、查询、等待、生成等哪个阶段，从而提升系统的透明度与交互信任感。

12. Web 端完整交互体验
当前项目主入口已经切换到 Web 版本，支持：
（1）对话式主界面；
（2）模式切换；
（3）主题切换和界面个性化；
（4）快捷查询建议；
（5）城市快速选择与定位辅助；
（6）关于页和使用说明读取；
（7）服务端流式回答（SSE）；
（8）Markdown 渲染与阅读体验优化。

13. 兼容演进能力
项目中仍保留了早期桌面端 UI 相关代码与打包配置，说明作品已经历从桌面交互到 Web 交互的演进。在竞赛展示中，这一点可体现出项目不是一次性 Demo，而是持续迭代、具备工程演进路径的完整作品。


四、技术方案

1. 总体架构概述
RailGPT 采用“Web 前端 + Flask 接口层 + 智能体核心 + 多源铁路工具层 + 记忆系统 + 知识检索系统 + 模型生成层”的总体架构。

系统整体流程可概括为：

用户输入
-> Web 前端界面
-> Flask 接口接收请求
-> 智能体主控模块进行路由与任务规划
-> 执行层并发调用铁路工具与知识模块
-> 记忆系统补充上下文
-> 答案生成模块整合事实并输出
-> 通过 SSE 流式回传到前端

2. 前端技术方案
当前前端主要由以下部分组成：
（1）templates/index.html：定义页面结构，包括主聊天区、侧边栏、会话区、建议区、观察面板、模式切换、主题设置等；
（2）static/js/app.js：负责页面交互逻辑、会话加载、消息发送、SSE 流式接收、对话状态切换、主题切换、快捷输入、城市选择等；
（3）static/css/styles.css：负责界面样式、布局、主题风格和交互表现。

前端的特点不是简单聊天气泡，而是围绕“铁路智能体交互”进行了功能性设计，包括：
（1）左侧会话管理；
（2）右侧观察面板；
（3）顶部模式切换；
（4）建议语句和快捷填充；
（5）对话内容的流式更新；
（6）与后端状态同步的交互逻辑。

3. 后端 Web 接口层
web_app.py 负责搭建 Flask 应用与对外接口。核心接口包括：
（1）首页加载；
（2）建议词获取；
（3）城市选择器；
（4）会话列表管理；
（5）会话加载、删除、重命名、导出；
（6）模式切换；
（7）聊天接口；
（8）状态查询；
（9）搜索接口；
（10）说明文档读取。

其中聊天接口采用流式返回机制，将智能体生成过程中的内容逐步推送给前端，而不是一次性等待全部结束再返回。这种设计一方面增强了产品体验，另一方面也更契合智能体“边推理边反馈”的交互特征。

4. 智能体主控架构
系统核心由 RailwayAgentApp 统一编排，其基本流程为：
（1）Router 识别意图，判断当前问题应进入哪一类任务；
（2）Planner 将识别结果转换为结构化任务计划；
（3）Executor 并发执行查询任务，并收集事实结果；
（4）AnswerGenerator 基于事实、上下文、知识与记忆生成最终答复；
（5）必要时根据 need_more_facts 再次规划下一轮查询；
（6）在多轮内完成补充检索、比较分析与最终总结。

这使得系统不是“模型直接回答”，而是“模型驱动 + 结构化任务执行 + 事实反馈再生成”的闭环智能体。

5. Router 路由层设计
Router 是系统意图理解与任务入口判断的核心模块。当前代码中，Router 不仅支持基础路由，还引入了更高级的快速模式与上下文增强策略，主要体现为：
（1）支持 fast-go、fast-plus、deep 等不同模式；
（2）能够结合当前会话中的车次、区间、日期、车组等锚点进行上下文路由；
（3）可在快速模式下使用轻量决策链路提升响应效率；
（4）引入铁路专用查询守卫与归一化逻辑，降低错误解析带来的误路由。

尤其重要的是，系统在路由阶段已经开始吸收上下文信息，而不是等到最终生成阶段才做“补救”。这体现了本作品在智能体设计上的前置控制思想。

6. Planner 规划层设计
Planner 的任务是把“用户问题”转化为“机器可执行的任务计划”。当前实现支持 query、analyze、compare、summarize、chat、pending 等动作类型。其特点包括：
（1）支持缺信息时生成 pending 任务，主动补问；
（2）支持将用户聊天意图与查询任务混合处理；
（3）支持在二轮、三轮推理中根据已有 facts 重新生成补充计划；
（4）对铁路对象 ID 进行标准化处理，例如车次大写、动车组编号规范化、区间对象保留站名结构等。

这使系统能够把自然语言问题转换成较稳定、可执行的结构化计划，是连接语言理解与工具执行的关键桥梁。

7. Executor 执行层设计
Executor 负责根据任务计划真正调用外部工具与本地模块。当前实现具有较强工程性：
（1）基于线程池进行有限并发执行；
（2）支持本轮去重和跨对话去重，避免重复请求；
（3）对 query、analyze、compare 等步骤进行分离处理；
（4）能够把空结果、错误结果、可重试错误与正常结果统一整理为标准事实结构；
（5）在执行结果中附加 fast_views 与 fast_candidates，为后续快速推理与压缩提供结构化候选信息；
（6）在必要时通过 PSW 把执行状态暴露给外部观察。

这一设计使项目不只是“能调接口”，而是具备了基本的并发调度、重试容错、结果标准化和可观测性。

8. LLM 与答案生成层
项目通过 llm/llm_client.py 接入大语言模型，并区分快速模型与深度模型两类用途。AnswerGenerator 负责把以下信息融合后生成最终答复：
（1）工具层返回的结构化 facts；
（2）知识检索模块返回的补充说明；
（3）当前会话上下文与记忆内容；
（4）Router 和上下文代理给出的辅助线索；
（5）当前模式下的生成策略。

同时，AnswerGenerator 还支持在必要时触发强制收束，避免智能体无限循环查询，保证用户能在合理时间内得到结果。

9. 快速模式与事实压缩机制
本项目的一项显著特色是引入了针对铁路场景的快速模式与事实压缩机制。fast-go 与 fast-plus 模式并不是简单地“少查一点”或“换个模型”，而是在路由、工具视图整理、事实候选提炼和最终生成策略上进行联动优化。

其中，FastFactCompressor 模块会对大量工具结果进行压缩、保留关键证据、提取高价值信息、生成候选事实，减少最终提示词负担，提高响应效率。这一部分既体现了算法创新，也直接面向工程瓶颈，是本作品的重要亮点。

10. 记忆系统设计
项目并未将对话上下文简单拼接到提示词中，而是设计了分层记忆系统，主要包括：
（1）SessionMemory：维护当前对话短期状态，记录最近消息、实体锚点、路线、日期、车次、站点、查询对象等；
（2）EpisodicMemoryStore：按会话或轮次记录阶段性快照，形成中期记忆；
（3）LongTermMemory：沉淀高频实体、偏好和长期上下文信息；
（4）EmbeddingIndex 与 MemoryEmbedder：为长期记忆检索提供向量支持；
（5）ConversationStore：把会话内容、标题、状态与导出逻辑统一管理。

分层记忆的意义在于：系统既能记住当前这一轮在说什么，也能记住之前讨论过的车次或区间，还能在合适时机把历史偏好作为辅助信息召回。

11. 铁路知识库与 RAG 检索
knowledge/railway_knowledge.py 构建了本地铁路知识库与检索增强机制。与完全依赖外部接口不同，项目通过本地缓存与知识抽取建立了站点档案、线路档案、车次档案等内容，并支持：
（1）实体命中检索；
（2）关键词匹配；
（3）图扩展；
（4）向量相似度召回。

这种“本地知识 + 动态工具”的组合设计，使系统在面对“解释型问题”时比纯查询更完整，在面对“事实型问题”时又能以实时数据为主，尽量避免过时知识干扰。

12. 铁路工具层设计
工具层是本项目区别于一般聊天系统的关键。当前项目已集成多类铁路数据工具：
（1）train_query：车次近期担当与动车组近期运行历史；
（2）path_query：列车径路、经停、停靠核验；
（3）station_query：站点信息查询；
（4）station_dict：站名、电报码字典与本地缓存；
（5）s2s_query：区间列车目录、基准、时段、图定/临客等分析；
（6）s2s_leftTicket_12306：12306 余票查询；
（7）transfer_12306：12306 中转查询；
（8）rail_store：本地 SQLite 缓存站点、径路和区间结果；
（9）rail_12306_store：12306 证书和查询缓存管理；
（10）http_12306：对官方站点访问进行会话、限流、重试、回退与异常判断。

可以看出，项目不只是把模型“接上 API”，而是围绕铁路场景构建了一整套工具层与缓存层。

13. 可观测性与状态机
PSW（程序状态词）是本项目很有答辩价值的一项工程设计。系统会在不同阶段暴露诸如 ROUTING、PLANNING、QUERYING、IN_FLIGHT、QUERY_HIT、WAITING、GENERATING、DONE、ERROR 等状态。前端观察面板可以显示这些状态，使用户和开发者都能看到系统当前处于什么阶段。

这种设计在竞赛答辩中很重要，因为它证明本作品不是黑盒式的“糊一个答案”，而是具备过程透明、状态清晰、便于调试和教学演示的工程能力。

五、核心创新点

1. 从“聊天模型”升级为“分析型铁路智能体”
本作品最大的创新不在于“接了一个大模型”，而在于把大模型放进了一个完整的智能体闭环中。系统可以路由、规划、执行、补问、回收结果、再次规划并最终生成答案，具备面向真实任务的分析行为。这与普通对话机器人有本质区别。

2. 面向铁路场景的专用路由与查询守卫
项目针对铁路领域中高频且容易混淆的对象，如车次、动车组、区间、日期、经停、余票等，设计了专门的归一化与守卫机制。其目的不是“让模型更会说”，而是让系统更少误解问题、更少发起错误查询、更少产生领域幻觉。

3. 快速模式下的 LLM 事实压缩算法创新
本项目并非简单堆砌大模型调用，而是在 fast-go、fast-plus 模式下设计了铁路场景专用事实压缩机制。FastFactCompressor 会对多源工具结果进行分层整理、证据保留与候选提取，减少最终提示词负担，提高响应速度，同时尽量保持回答质量。这一部分既有算法思想，也有工程落地，是作品非常适合重点答辩的创新点。

4. 多级记忆体系增强连续对话能力
项目设计了短期记忆、中期情节记忆、长期记忆与向量召回机制，使系统不仅能回答当前问题，还能继承用户在之前轮次中提到的车次、日期、区间与偏好。这样的设计明显优于“只拼接最近几轮对话”的简单上下文方法。

5. 动态数据与静态知识的融合
项目并没有把所有问题都交给外部接口，也没有只依赖本地知识库，而是通过“真实工具查询 + 本地知识检索增强”的方式分工协作：
（1）动态事实类问题优先依赖实时或近实时工具；
（2）解释说明类问题由本地知识库提供背景补充；
（3）最终回答由答案生成模块统一整合。

这一设计提升了系统在准确性与表达完整性之间的平衡能力。

6. 面向用户的可观测推理过程展示
很多智能体系统在内部确实做了多步处理，但用户看不到。RailGPT 通过 PSW 与思考面板，把路由、规划、查询、等待、生成等过程可视化，既有利于调试，也有利于答辩展示。这一设计兼具技术价值和演示价值。

7. 面向真实网络环境的缓存、限流与容错设计
铁路数据接口并不总是稳定，尤其官方链路存在限流、证书、波动和维护窗口等问题。本项目在工具层设计中加入本地缓存、指数退避、过期回退、查询结果标准化、证书缓存和数据库持久化机制，体现了较强的工程完整性。

8. 前后端一体化交互设计
项目不是“后端很强，前端很简陋”的纯技术演示，也不是“前端漂亮，后端空心”的壳子。它把智能体结果流、会话存档、思考观察面板、模式控制和铁路场景快捷交互整合在一起，形成了较完整的产品形态。


六、重难点与解决方法

1. 难点一：铁路自然语言中的实体识别复杂
铁路问题中，用户可能输入站名简称、口语化表达、模糊日期、简写车次，甚至一句话里混杂多个对象。例如“明天宁杭最快的高铁”“G1 停不停济南西”“这趟车还有票吗”。如果系统不能正确拆分实体，后续所有工具调用都会出错。

解决方法：
（1）在 Router、实体解析器、查询守卫中加入铁路专用规则；
（2）对车次、动车组编号、区间 ID、日期做标准化；
（3）通过 SessionMemory 记录上文锚点，辅助补全省略信息；
（4）在无法稳定识别时，不盲答，转为 pending 补问。

2. 难点二：多轮对话中如何保持上下文一致
用户真实提问常常是层层递进的。如果系统每轮都从零开始理解，不仅体验差，也会丢失信息。

解决方法：
（1）SessionMemory 保存近期消息、车次、区间、日期、对象类型等锚点；
（2）EpisodicMemoryStore 记录阶段性快照；
（3）LongTermMemory 沉淀高频实体与长期偏好；
（4）ConversationStore 支持会话级状态恢复；
（5）Planner 和 Router 都能利用这些记忆结果，而不是仅在最终生成时使用。

3. 难点三：外部铁路数据源存在波动和限制
铁路相关接口并非为竞赛作品定制，实际使用中可能出现超时、限流、空返回、HTML 封禁页、凌晨维护窗口等问题。

解决方法：
（1）在 12306 访问层加入统一会话、频率限制和异常识别；
（2）使用退避重试策略处理临时失败；
（3）采用本地 SQLite 缓存站点、路径、区间和证书信息；
（4）区分 retryable error 与 non-retryable error；
（5）在必要时使用缓存回退，降低接口波动对体验的影响。

4. 难点四：如何避免大模型在缺失信息时“编答案”
这是竞赛评委最容易关注的问题之一。尤其铁路场景非常容易被用户当场验证，一旦出现“编造经停、编造余票、编造担当”就会严重影响可信度。

解决方法：
（1）系统采用“先查事实，再生成答案”的流程，而不是让模型凭语言经验直接作答；
（2）对工具结果统一封装为 facts，答案生成尽量建立在事实基础上；
（3）在信息不足时进入 pending，而不是硬生成结论；
（4）引入铁路知识库时，坚持“动态事实优先，本地知识辅助”的原则；
（5）通过多轮 need_more_facts 机制让系统自动补查缺失事实。

5. 难点五：铁路场景中既要快，也要准
如果每个问题都走完整深度推理链路，系统会变慢；但如果过度追求快，又可能损失准确度。

解决方法：
（1）设计 fast-go、fast-plus、deep 三种模式；
（2）通过 FastFactCompressor 压缩冗余信息；
（3）通过 fast_views 和 fast_candidates 在工具结果层提前提炼关键事实；
（4）通过 FastPlusContextAgent 在前置阶段提升路由效率；
（5）必要时强制收束，避免无限循环。

6. 难点六：前端如何真实呈现智能体工作过程
许多系统看似智能，但用户只能看到“请求中”和“已完成”两个状态，不利于理解和展示。

解决方法：
（1）引入 PSW 状态机，把关键阶段结构化定义；
（2）前端观察面板专门展示状态和思考流；
（3）聊天接口采用 SSE 流式推送，使用户感受到系统正在逐步生成内容；
（4）将会话管理、模式切换和建议输入集成到统一界面中，形成更完整的人机协作体验。

7. 难点七：铁路未来日期查询的真实性判断
某些路径或图定信息在未来日期未必能直接通过单次接口查询获得，需要结合缓存和运行规律判断。

解决方法：
（1）在路径查询与本地存储中记录路径有效期和运行日期信息；
（2）必要时结合最近日期数据进行辅助推断；
（3）在最终回答中以事实为核心，避免做超出证据范围的夸大结论。

为了比赛现场演示顺畅，建议按以下顺序操作：
（1）先展示首页与会话管理；
（2）演示一个简单问题，例如站名或电报码查询；
（3）演示一个动态问题，例如余票或经停查询；
（4）演示一个多轮追问问题，体现上下文记忆；
（5）演示观察面板，说明系统并非黑盒；
（6）若网络不稳定，准备录屏作为兜底材料。

6. 运行注意事项
（1）涉及真实铁路接口时，响应时间可能受网络与外部平台状态影响；
（2）凌晨维护时段部分接口可能不稳定；
（3）若正式答辩使用在线接口，建议提前准备截图与视频备份；
（4）若需要打包发布，可结合项目现有发布与运行时资源初始化逻辑处理。
