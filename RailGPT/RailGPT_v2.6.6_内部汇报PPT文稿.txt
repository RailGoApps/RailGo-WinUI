第2页：一句话定义项目
==================================================
页标题
RailGPT 到底是什么

页面内容
1. RailGPT 不是“直接让 LLM 回答铁路问题”的问答机器人。
2. 它是一个“由 Router、Planner、Executor、AnswerGenerator、Memory、UI 共同组成”的铁路分析 Agent。
3. 系统核心思想是：先识别意图，再决定查什么工具，再拿到真实世界证据，再由 LLM 基于事实完成结构化生成。
4. 因此，它追求的是“工具驱动的真实回答”，而不是“提示词堆出来的像真回答”。
5. 从项目 README 的版本原则看，v2.x 的核心目标是不推翻主控制流，而是在稳定内核上持续增加世界接口能力和推理稳健性。

汇报备注
可强调“分析型 Agent，不是编故事模型”。这句话很适合放大展示。

第3页：项目要解决的真实问题
==================================================
页标题
为什么要做 RailGPT

页面内容
1. 铁路问题天然复杂，不是单跳问答。
2. 用户常问的问题包含多种类型：
   - 区间最快车、标杆车、担当路局
   - 某车次是否停某站、运行路径、时刻表
   - 某天区间余票
   - 某路线中转方案
   - 某车次最近动车组担当与车型稳定性
3. 这些问题的共同特征：
   - 强依赖实时或准实时数据
   - 问法高度口语化
   - 上下文省略很多，例如“这几趟”“这条线”“推荐的那些车”
   - 单靠 LLM 常常会幻觉、跳步或忘上下文
4. 因此系统必须同时解决：
   - 意图识别
   - 工具选择
   - 参数归一化
   - 多轮补查
   - 上下文连续性
   - 结果可解释

第4页：项目设计总原则
==================================================
页标题
RailGPT 的五个设计原则

页面内容
1. 稳定优先：README 明确 v2.0 之后不再推翻 Router / Planner / Executor 核心控制流。
2. 事实优先：所有关键铁路结论必须建立在工具返回事实之上。
3. 工具优先：让 Agent 的能力来自可调用工具，而非单纯 prompt 复杂度。
4. 可观测优先：PSW 状态系统、Thinking 面板、调试日志共同暴露执行过程。
5. 上下文优先：通过 SessionMemory、MemoryManager、FAST-PLUS context agent 共同解决省略、追问、跨轮衔接问题。

汇报备注
这里可以加一句：项目不是为了“让模型更聪明”，而是为了“让系统更可靠地理解世界”。

==================================================
第8页：核心执行闭环
==================================================
页标题
一次用户请求如何流经系统

页面内容
1. 用户输入先进入 `RailwayAgentApp._run_core_loop()`。
2. 系统先做 `_prepare_memory_for_turn()`，把会话记忆、情节记忆、长期偏好回忆出来。
3. 进入 Router 阶段，生成初始任务列表。
4. 进入 Planner 阶段，把任务整理成可执行 plan。
5. 进入 Executor 阶段，并发查询工具，获得 facts。
6. 如果 facts 不够，AnswerGenerator 会返回 `need_more_facts`，Planner 再补 plan。
7. 如果缺少关键槽位，系统会返回 `pending`，进入 follow-up 模式。
8. 如果事实足够，系统进入最终回答生成。
9. 回答结束后写回 SessionMemory、EpisodicMemory、LongTermMemory。

汇报备注
这页要突出“多轮自治闭环”而不是“一次性答复”。

==================================================
第9页：三种模式的整体定位
==================================================
页标题
FAST-GO / FAST-PLUS / DEEP 模式分工

页面内容
1. FAST-GO：
   - 目标：速度优先
   - 路由和中间阶段走 fast
   - 最终回答也走 fast
   - 适合高频、清晰、证据充分的请求
2. FAST-PLUS：
   - 目标：在 fast 链路上解决上下文断裂
   - 路由前额外接入一个重型但稳定的 context agent
   - 中间规划和工具执行仍保持 fast 链路
   - 最终回答切到 deep final llm
   - 是当前上下文治理的重点链路
3. DEEP：
   - 目标：重型、稳定、完整推理
   - 保持原有深推理主链路，不为低延迟妥协
   - 是系统的重型稳定服务链路

汇报备注
这页可以直接回答“为什么不是所有模式都走同一套逻辑”。

==================================================
第10页：为什么要引入模式分流
==================================================
页标题
速度、稳定性、上下文连续性三者如何平衡

页面内容
1. 纯 deep：稳定但慢，用户等待成本高。
2. 纯 fast：快，但在上下文连续追问时更容易断上下文。
3. 因此项目没有选择单一模式，而是做了模式分流：
   - 常规快问快答走 FAST-GO
   - 上下文敏感且希望低时延的场景走 FAST-PLUS
   - 深度分析与高稳定需求走 DEEP
4. 这是一种工程层面的折中：
   - 不是追求“所有链路都最强”
   - 而是让不同场景都能落到更合适的服务链路上

==================================================
第11页：Router 的角色
==================================================
页标题
Router 不是简单分类器，而是任务编译器

页面内容
1. Router 的输出不是标签，而是 task 列表。
2. task 可以是：
   - `query`
   - `pending`
   - `chat`
   - `analyze`
   - `compare`
   - `summarize`
3. 这意味着 Router 的职责是把自然语言请求编译成后续 Agent 可执行的任务计划草案。
4. Router 内部既有规则，也有专家，也有 LLM 仲裁，也有后备路径。
5. 当前 Router 已经支持：
   - 区间车次查询
   - 标杆车
   - 余票
   - 中转
   - 车次经停 / 路径 / 终到
   - 车底担当 / 智能动车识别
   - 电报码、站名反查、站点元数据
   - 会话型聊天

==================================================
第12页：Router 的四层决策结构
==================================================
页标题
当前路由器不是单一路由，而是四层保险

页面内容
1. 第一层：FAST-PLUS context agent 预处理
   - 只在 FAST-PLUS 启动
   - 先把模糊追问改写成更自洽的独立意图
2. 第二层：fast experts 并行提案
   - 多个专家各自判断是否命中
   - 最高置信提案直接出任务
3. 第三层：compact fast llm 仲裁
   - 如果专家没命中，再用轻量 LLM 做压缩仲裁
4. 第四层：legacy router prompt fallback
   - 如果 fast 路径仍失败，再落回传统 Router 提示词路径
5. 整体目标：
   - 先尽量用确定性和专家规则提速
   - 不行再用 LLM
   - 再不行还有兜底，不让系统裸崩

==================================================
第13页：上下文问题为什么难
==================================================
页标题
RailGPT 面临的上下文断裂本质是什么

页面内容
1. 用户经常不会重复完整问题。
2. 真实追问常常是这种形式：
   - “那这几趟哪个是南昌局的？”
   - “推荐的这些车里哪个更稳？”
   - “它明天有票吗？”
   - “这条线还有更快的吗？”
3. 对人来说这些引用是自然的，但对 fast 链路中的路由专家来说，省略代词、多轮指代、日期继承都很容易丢失。
4. 如果上下文断掉，后果通常不是报错，而是：
   - 路由成 chat
   - 重新开一个错误主题
   - 少查关键工具
   - 问用户已经说过的信息
5. 这类错误对用户体验伤害非常大，因为会显得“明明刚说过，系统却忘了”。

==================================================
第14页：FAST-PLUS Context Agent 的设计目标
==================================================
页标题
为什么新增一个上下文 Agent

页面内容
1. 该 Agent 是一个“前置意图整形器”。
2. 它不直接回答问题，也不直接查工具。
3. 它的职责只有一个：
   - 在进入专家路由前，把当前用户输入改造成一个更自洽、更完整、更稳定的意图表示。
4. 它主要解决的不是知识问题，而是引用解析问题：
   - 这几趟是哪些车
   - 这条线是哪个区间
   - 明天是哪一天
   - 推荐的这些选项分别是谁
5. 工程定位上，它是一个重型但稳定的前置模块，只在 FAST-PLUS 触发，以减少时延影响。

==================================================
第15页：Context Agent 的输入输出结构
==================================================
页标题
Context Agent 实际产出什么

页面内容
1. `agent/context_agent.py` 中的 `FastPlusContextAgent` 输出一个 JSON 结构。
2. 关键字段包括：
   - `intent_category`
   - `rewritten_user_text`
   - `resolved_route`
   - `resolved_train_numbers`
   - `resolved_emu`
   - `resolved_date`
   - `resolved_station_mentions`
   - `resolved_query_object`
   - `confidence`
   - `reason`
3. 这等于在后续专家路由前，先生成一个“可机器消费的上下文整理结果”。
4. 如果用户是在聊天，intent_category 会直接标成 `chat`。
5. 如果是铁路追问，它会尽量把问题改写成独立可理解的请求。

汇报备注
这页很适合配一个例子：用户说“那它明天有票吗”，整理后变成“请查询南京南-福州在 2026-03-30 的余票情况”。

==================================================
第16页：Context Agent 如何保证稳定性
==================================================
页标题
上下文 Agent 不是裸奔 LLM，而是带保险的

页面内容
1. 使用 deep 模式 LLM 作为默认模型，强调稳定而非极限速度。
2. 设置 18 秒超时，避免前置模块无限拖慢链路。
3. 有内部 cache，同一上下文不会重复整理。
4. 即使 LLM 超时或失败，也有 heuristic fallback。
5. heuristic 能覆盖若干高频意图：
   - train_assignment
   - train_path
   - train_overview
   - route_ticket
   - 社交闲聊
6. 测试文件 `agent/test_context_agent.py` 已覆盖：
   - 超时回退到 heuristic
   - 相同上下文命中缓存

==================================================
第17页：Context Agent 如何接入整条链路
==================================================
页标题
上下文整形不是孤立功能，而是贯穿前后链路

页面内容
1. 在 `router.py` 中，只有 `fast-plus` 模式会调用 `_run_context_agent()`。
2. 其结果会写入 `SessionMemory.context_agent_state`。
3. Router 在构造 fast route context 时，会优先使用高置信度的 `rewritten_user_text`、`resolved_route`、`resolved_train_numbers` 等信息。
4. AnswerGenerator 在 fast 模式下构造 prompt 时，也会把 context-agent context 注入进去。
5. 这意味着上下文整理结果不仅影响“怎么路由”，也影响“怎么最终生成”。
6. 这是本项目当前解决上下文断裂的关键机制，也是挑战赛场景下最有代表性的创新点之一。

==================================================
第18页：为什么只在 FAST-PLUS 开启 Context Agent
==================================================
页标题
上下文能力为什么不是全模式硬开

页面内容
1. 因为前置 context agent 是重型模块。
2. 如果对所有 fast 请求都强制执行，会显著抬高平均延迟。
3. 项目当前策略是：
   - FAST-GO：旁路 context agent，极致快
   - FAST-PLUS：启用 context agent，解决上下文断裂
   - DEEP：保持原有深链路，不做这次改动
4. 这样做的本质，是把“上下文稳定性增强”做成可控开关，而不是全局强制成本。
5. 从产品视角看，这也是一种更合理的服务分层策略。

==================================================
第19页：Planner 的角色
==================================================
页标题
Planner 负责把路由任务变成可执行计划

页面内容
1. Router 产出的 task 仍可能带有口语化参数。
2. Planner 做的事情包括：
   - query id 规范化
   - 站名 / 电报码规则处理
   - 日期默认补全
   - pending 优先级处理
   - summarize 自动补齐
   - follow-up 的 plan 生成
3. Planner 的关键价值是“让 Router 输出安全落地到 Executor”。
4. 它相当于 Agent 内部的中间编译层。

==================================================
第20页：Planner 的参数规范化策略
==================================================
页标题
为什么 Planner 对不同对象采用不同归一化

页面内容
1. `train / path_detail / path_future / path_past`
   - 统一车次大写
   - 去掉“次”
2. `path_stopcheck`
   - 保留“车次列表|车站列表”的矩阵格式
3. `emu`
   - 严格规范动车组编号，拒绝模糊缩写
4. `left_ticket_s2s / transfer_12306 / station_to_station* / s2s_*`
   - 保留原始站名区间，不擅自转电报码
5. `telecode`
   - 输入必须是站名
6. `name`
   - 输入必须是三位电报码
7. `station`
   - 必要时将站名转为电报码
8. 这套细粒度规则的意义是避免“同样是车站信息，不同工具却需要不同参数格式”带来的错查。

==================================================
第21页：Executor 的角色
==================================================
页标题
Executor 是系统与真实世界交互的总调度器

页面内容
1. Executor 负责并发执行 query 类任务。
2. 当前采用 ThreadPoolExecutor 做有限并发。
3. 支持：
   - 本轮去重
   - 对话级去重
   - 参数 preflight
   - query hit / empty / error 分类
   - chat/analyze/compare 的副任务处理
4. 结果统一收敛为 `facts` 结构：
   - `queries`
   - `analysis`
   - `comparisons`
   - `meta.errors / warnings / chat_messages / pending`
5. 这让后续生成器面对的是统一事实结构，而不是杂乱工具回包。

==================================================
第22页：Executor 的可靠性设计
==================================================
页标题
Executor 如何避免工具层把系统拖垮

页面内容
1. preflight 阶段会对区间型参数进行保护性校验。
2. 如果线路无法稳定识别，不硬查，直接转 `pending` 追问。
3. 本轮重复 query 会被跳过。
4. 同一对话中已经查过且无需重试的 query 会被跳过。
5. 空结果不会直接当崩溃处理，而是区分：
   - 维护窗口造成的不可靠空结果
   - 白天真实空结果
6. 错误会带 `retryable` 标记，便于 Planner 决定是否补查。
7. 从工程角度看，Executor 是把“不确定外部 API”驯化成“可控内部事实流”的关键模块。

第23页：Rail 工具层能力版图

页标题
目前系统已经接入了哪些铁路工具

页面内容
1. 车次 / 动车组：

2. 路径 / 经停：
   - `path_detail`

==================================================
第24页：Fast 链路为什么还能快
==================================================
页标题
FastCoordinator 与 FastFactCompressor 的价值

页面内容
1. 快链路不是简单少做事，而是做“证据压缩”。
2. `FastFactCompressor` 会把事实切成多个 lane 并行处理。
3. 每个 lane 提取 candidate，再全局合并。
4. 输出的不是原始大 JSON，而是压缩后的 context bundle：
   - merged candidates
   - observations
   - retained evidence
   - source stats
5. `FastCoordinator` 会并行准备三份资产：
   - context_bundle
   - RAG payload
   - presentation_plan
6. 这让最终生成时，模型面对的是更小但仍有依据的证据包，因此更快。

==================================================
第25页：FastCoordinator 的三份资产分别干什么
==================================================
页标题
为什么快链路里还要做协调器

页面内容
1. `context_bundle`
   - 用于把原始 facts 变成更紧凑的证据表示
2. `rag_context`
   - 用于补充静态铁路知识
   - 但对于动态工具型查询会被主动跳过，避免知识污染实时事实
3. `presentation_plan`
   - 提前告诉最终生成器，这一题更适合排行榜、票务快照、经停矩阵还是查询卡片
4. 当前 presentation plan 已能根据 query object 自动切换回答骨架：
   - ranked_trains
   - ticket_snapshot
   - transfer_options
   - timetable_or_stop_matrix
   - lookup_card
5. 测试 `agent/test_fast_coordinator.py` 已验证并行资产构建与缓存行为。

==================================================
第26页：AnswerGenerator 的双层模式设计
==================================================
页标题
为什么回答生成器里也有模式分工

页面内容
1. AnswerGenerator 里实际存在两套模型语义：
   - pipeline llm：处理中间阶段结构化判断
   - final llm：处理最终自然语言生成
2. 模式映射关系：
   - FAST-GO：pipeline=fast，final=fast
   - FAST-PLUS：pipeline=fast，final=deep
   - DEEP：pipeline=deep，final=deep
3. 这意味着 FAST-PLUS 的设计核心不是“整条链路都 deep”，而是“前面快，最后稳”。
4. 对用户体验来说，这能在不完全牺牲响应速度的前提下，提升最终回答质量和上下文保持能力。

==================================================
第27页：Fast 模式下的最终回答为什么更稳
==================================================
页标题
Fast 链路不是直接瞎答，而是有明确的证据协议

页面内容
1. 如果 fast mode 已经拿到压缩证据 context bundle，AnswerGenerator 会进入 compact fast answering。
2. prompt 中明确要求：
   - 只基于 merged fast context 回答
   - 不能杜撰列车和票务信息
   - 推荐要显式排序
   - 保持简洁而准确
3. 在结构化阶段，模型只能输出：
   - `final`
   - `need_user_input`
   - `need_more_facts`
4. 这相当于给快链路加了一层“格式化决策协议”，减少随意发挥。
5. 如果证据已经足够，系统还可以直接 fast direct final，跳过不必要的补查。

==================================================
第28页：Memory 系统总览
==================================================
页标题
当前项目如何做记忆，而不是只靠聊天历史

页面内容
1. RailGPT 当前已经形成多层记忆体系：
   - SessionMemory：当前会话工作记忆
   - EpisodicMemory：同会话情节记忆
   - LongTermMemory：长期偏好记忆
   - ConversationStore：对话存档与恢复
2. 记忆不仅是“保存聊天记录”，而是“保存结构化实体与锚点”。
3. 这对铁路场景尤其重要，因为用户追问时大量引用的是：
   - 上一个区间
   - 上一个车次
   - 上一个日期
   - 上一个查询对象
4. 这些内容如果只保存在原始文本里，后续难以稳定复用；保存成 anchor 和 entity pool 就能直接服务路由和生成。

==================================================
第29页：SessionMemory 是如何解决当前轮上下文的
==================================================
页标题
工作记忆不是聊天数组，而是锚点系统

页面内容
1. `SessionMemory` 会维护多种 anchor：
   - last_train
   - last_emu
   - last_route
   - last_dep
   - last_arr
   - last_date
   - last_query_type
   - last_object
2. 同时维护 recent entity pool：
   - trains
   - emus
   - routes
   - dates
   - stations
   - objects
3. 还维护：
   - follow-up state
   - memory recall bundle
   - context agent state
4. 这使得系统可以在后续轮次中直接 resolve anchor，而不是每次重新猜测。

==================================================
第30页：Episodic Memory 与 Long-Term Memory 的价值
==================================================
页标题
为什么还需要情节记忆和长期记忆

页面内容
1. EpisodicMemory 记录的是同一会话内每一轮的摘要、实体、query objects。
2. LongTermMemory 记录的是长期关注热点，例如：
   - 某条路线被问过很多次
   - 某类对象被连续关注
3. Recall 时，系统会综合：
   - 当前 Session anchors
   - 同会话历史快照
   - 长期关注模式
4. 得到一个 `recall_bundle`，其中还会自动补 `anchor_candidates`。
5. 这套设计的核心意义是：
   - 用户不用每轮重说完整实体
   - 系统能更稳地理解“这条线”“这趟车”“还是那个问题”

==================================================
第31页：Memory RAG 的工程实现特点
==================================================
页标题
记忆系统为什么不是简单关键词匹配

页面内容
1. 当前 MemoryManager 支持 embedding。
2. Episodic 与 LongTerm 都有向量缓存文件。
3. Recall 排序不是单一分数，而是混合分数：
   - 实体重合
   - token 重合
   - anchor 命中
   - embedding 相似度
   - 时间新近性
4. 索引是后台异步建立的，不阻塞主对话。
5. 测试文件 `memory/test_memory_rag.py` 已验证：
   - episodic embedding score 生效
   - long-term embedding score 生效
   - 冷启动时规则召回不被 embedding 阻塞
   - 后台索引事件与去重逻辑正常

第32页：Knowledge RAG 的定位
==================================================
页标题
为什么项目里既有工具事实，又有知识检索

页面内容
1. 工具层主要负责动态事实，例如：
   - 当天余票
   - 某天列车运行
   - 某车次路径
2. 知识层主要负责静态或半静态知识，例如：
   - 站点档案
   - 缓存中的站点元数据
   - 典型路径信息
   - 路由相关知识片段
3. `FastCoordinator` 会根据 query object 判断是否跳过 RAG：
   - 动态工具问题跳过，防止静态知识污染实时结论
   - 静态查询则保留 RAG 增强
4. 这是一种非常关键的系统边界设计：
   - 知识可以辅助理解
   - 但不能压过实时证据

为什么这个项目“可调试、可解释”

3. PSW 的核心价值：
   - 用户不再盲等
   - 开发者知道链路慢在哪
   - 问题可以定位到具体阶段
4. 对一个 Agent 项目来说，这比“多加一点 prompt 技巧”更重要。
